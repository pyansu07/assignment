# Assumptions

- **IDs and timestamps** are generated by the database (`gen_random_uuid()`, `clock_timestamp()`); clients can never supply them. Unknown body fields are rejected with 400.
- **Money** is `NUMERIC(19,4)`: max 15 integer digits, max 4 decimals, single implicit currency. Amounts must be strictly positive. Input with more precision, exponents, signs or non-numeric text is rejected, never rounded. Amounts are accepted as strings (preferred) or plain JSON numbers; responses are always strings with 4 decimals.
- **Balance ceiling:** a credit that would push a balance past ~10^15 returns `409 BALANCE_LIMIT_EXCEEDED` with no effect.
- **Duplicate references:** `reference_id` is unique per account (not globally). A repeat for the same account returns `409 DUPLICATE_REFERENCE` (plus the original record in `details.existing`); nothing is written. The original request's amount/type are not compared. Duplicate detection takes precedence over the insufficient-funds check.
- **Rejected requests do not consume the reference:** a debit rejected for insufficient funds can be retried with the same `reference_id`.
- **Required fields:** `description` is required (1–500 chars, trimmed); `reference_id` 1–100 chars; account `name` 1–100 chars, trimmed.
- **Invalid ids:** a malformed UUID is `400`; a well-formed but unknown account is `404`.
- **Pagination:** `page` default 1, `limit` default 20, max 100. Out-of-range pages return an empty list (200), not an error. An account with no transactions has `total_pages: 0`.
- **Ordering:** `created_at DESC`, then `id DESC` as a deterministic tie-breaker.
- **Errors:** uniform `{ "error": { code, message, details? } }`; internal errors never leak SQL or stack traces.
- **Transfers:** both accounts must exist and differ; `reference_id` is required and makes the call idempotent per source account (a repeat returns 409 and changes nothing). A transfer creates one `transfers` row and two immutable ledger entries (debit on source, credit on destination, shared `transfer_id`, entry reference `transfer:<transfer id>`). Transfers appear in each account's normal history.
- **Idempotency-Key (optional header):** supported on transactions and transfers; absent header = unchanged behaviour. Scope is the account (the source account for transfers). A replay returns the original `201` body plus `Idempotent-Replayed: true`; the same key with a different payload (including a different operation type) returns `409 IDEMPOTENCY_KEY_REUSED`. Only successful operations are recorded - a failed or rolled-back request does not consume its key. Amounts are compared numerically (`"10"` = `"10.00"`). Keys are 1-255 characters, never expire, and only a SHA-256 fingerprint plus the response body is stored. The header is optional rather than mandatory so existing clients keep working.
- **No reversals/edits:** transactions are immutable; corrections are made with new compensating transactions.
- **Excluded:** authentication/authorization, rate limiting, multi-currency, account listing/deletion, soft deletes, CORS (not needed for a server-to-server API).
